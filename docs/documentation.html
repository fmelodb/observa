What it is

A post-mortem cockpit, not a monitor

Observa exists for one situation: the incident is over, somebody wants an explanation, and all you have is an AWR export and a pile of logs. You describe the problem, point it at an AWR repository, and a team of specialist LLM agents works the case across several reflection turns — querying DBA_HIST_*, grepping the files you attached, publishing findings to a shared blackboard that the other specialists read before their next turn.

What separates it from pasting an AWR report into a chat window is that every claim is traceable. Each query and each file read is logged with a stable identifier; findings cite those identifiers; references to evidence that was never gathered are dropped before you ever see them. A finding that survives with no citation is displayed as ○ uncited rather than quietly blending in with the ones that earned their place.

Observa does not decide anything. It produces a hypothesis with its working shown, for a DBA to accept or reject.

Prerequisite concept

The AWR repository model

Observa expects to connect to an AWR repository — a separate database into which you imported the production system's AWR data with awrload.sql, after extracting it there with awrextr.sql. It does not connect to the ailing database itself.

This single decision explains most of the product's behaviour:

RuleReason
V$ / GV$ rejectedThey describe the repository instance you are connected to — the wrong machine entirely.
Every query filters dbidOne repository can hold snapshots from many source databases.
Version and topology from DBA_HIST_DATABASE_INSTANCEThe historical record of the source instance, rather than the local one.
Zero rows is a valid answerSpecialists abstain on an empty result instead of reporting a broken connection.
Licensing

Querying DBA_HIST_* / AWR requires the Oracle Diagnostics Pack, licensed separately from the database. Observa neither grants nor verifies that entitlement. Confirming that your organization is licensed for the data you point it at is your responsibility.

Getting it

Installation

# clone and install
git clone https://github.com/fmelodb/observa
cd observa
uv sync --group dev

# only if you plan to use OCI Generative AI
uv sync --extra oci

The oci extra pulls the Oracle Cloud SDK and langchain-community. Skip it entirely if you are on Anthropic or OpenAI.

First run

Setup

  1. Register a SQLcl saved connection

    Observa connects by name — it never assembles a connect string of its own, and it never handles your database password. Create the connection once, in SQLcl:

    <sqlcl_path>/sql /nolog
SQL> connect observa/<password>@<host>:<port>/<service>
SQL> conn -save observa
SQL> exit

    The name you pass to conn -save is what goes into mcp.sqlcl_connection_name. If that name doesn't exist, Observa fails at startup with an error listing the connections SQLcl actually has saved — it will not fall back or guess.

    Why NLS gets normalized

    Immediately after connecting, Observa issues a fixed set of ALTER SESSION statements pinning the date, timestamp and numeric formats. This is not cosmetic. In a comma-decimal locale (pt-BR, de-DE and friends) the default formats embed commas inside values, which corrupts SQLcl's CSV output and silently shifts columns.

  2. Create your config file

    cp config/config.example.yaml config/config.yaml

    config/config.yaml is git-ignored: it holds absolute paths and, if you use OCI, a compartment OCID that identifies your tenancy. The template is committed; your filled-in copy is not.

  3. Set your provider credentials

    One LLM key is mandatory. See Environment for the full list.

    export ANTHROPIC_API_KEY=sk-ant-...
# optional — only used by `setup check` to probe the repository
export ORACLE_PWD=...

  4. Run the pre-flight check

    uv run observa setup check

    It verifies, independently: the Python dependencies, the LLM API key for every model your config references, the config file itself, the SQLcl binary, the existence of the saved connection, OCI credentials when the OCI provider is configured, and Oracle reachability.

    [OK] proceeds. [WARN] is survivable — a missing ORACLE_PWD only disables the connectivity probe. [FAIL] must be resolved; the command exits non-zero.

Configuration reference

turns:

The three knobs that decide what a case costs in tokens and wall-clock time.

countint · 2

How many reflection turns to run. Turn 1 is cold — every active specialist works from the problem statement and the deterministic probes. From turn 2 on, each agent reads the blackboard digest of what everyone else found, which is where cross-specialty reasoning appears.

One turn is a fan-out, not an investigation. Three is thorough and roughly 50% more expensive than two.

time_budget_secondsint · 120

Per-turn watchdog. An agent that overruns is cancelled and records an explicit abstain with the reason — it never becomes a silent gap in the blackboard.

Raise it for slow reasoning models or a loaded repository; agents that consistently time out produce nothing but still cost tokens.

max_concurrent_agentsint · 4

How many specialists may call the LLM at once. This is your rate-limit valve: too high and you spend the turn in 429-backoff, which the wrapper handles by sleeping 60 seconds per retry.

Configuration reference

case:

Defaults for the intake screen's snapshot timeline.

timeline_daysint · 15

How much snapshot history to plot on the intake timeline. Only affects what you can see and click when choosing windows.

baseline_offset_daysint · 7

The auto-suggested baseline is the same time-of-day range this many days before the problem window. Seven lands on the same weekday, which usually matches the workload shape better than yesterday does. You can always override the suggestion by hand.

Configuration reference

agents:

enable_hypothesesbool · true

Runs hypothesis synthesis and contradiction detection after consolidation. Disabling it skips straight from the summary to verification.

enable_covebool · true

Runs the replay-verification pass — the mechanical tail that re-executes each cited piece of evidence and checks whether it actually supports the claim. Turning it off makes runs faster and the confidence figure less trustworthy.

contradiction_thresholdfloat 0–1 · 0.3

How much two hypotheses must conflict before a resolution round is triggered. Lower means more debates.

verification_support_thresholdfloat 0–1 · 0.7

If the verification pass scores evidential support at or above this, confidence is left alone. Below it, the support score itself becomes a multiplier applied to the summary's confidence — a summary whose evidence half held up reports roughly half the confidence.

agents.refinement

Between turns, Observa decides which specialists are still worth running. This is the main cost control in a long case: an agent that found nothing and that nobody referenced does not get a second turn.

enabledbool · true

Turn off to run every enabled agent in every turn.

universal_agentslist · [wait_time, ash]

Never dropped, whatever they found. Wait time and ASH are the orientation instruments for any Oracle performance case; losing them mid-investigation blinds everyone else.

keep_severitieslist · [high, critical]

A finding at one of these severities keeps its author active for the next turn.

enable_cross_referencebool · true

Also keeps an agent when another specialist's findings mention its territory — so the I/O agent survives if the SQL agent starts talking about physical reads, even though I/O itself found nothing yet.

min_activeint · 4

Safety floor. Refinement will never reduce the roster below this many agents.

agents.enabled

A master switch per specialist. Note that the topology_probe already skips agents whose subsystem is absent — there is no need to disable rac, exadata or dg on a single-instance non-Exadata database; the probe does it and records why.

ashActive Session HistorySession-level sampling, blockers, top consumers. Always active.
sqlSQL & PlansStatement-level regressions and plan changes.

Configuration reference

mcp:

sqlcl_pathabsolute path

The SQLcl launcher — sql.exe on Windows, sql elsewhere. Observa spawns it as an MCP stdio subprocess; it is never on your PATH by assumption.

# Windows — note the escaped backslashes
sqlcl_path: "D:\\sqlcl\\bin\\sql.exe"
# Linux / macOS
sqlcl_path: "/opt/sqlcl/bin/sql"
sqlcl_connection_namestring

The saved connection from Setup step 1. Observa calls SQLcl's connect tool with this name right after MCP initialization.

query_row_limitint · 50

Hard cap on rows handed back to an agent from any single query. Results are truncated, never silently — the tool payload carries a truncated flag the agent is instructed to respect. Raising this inflates prompt size fast.

enforce_windowwarn reject off

What happens when an agent writes a query with no snap-window restriction, so it would scan the whole retention period instead of the incident.

warn — the default. The query runs and the result carries a warning the agent must account for.
reject — the query is refused and the agent must rewrite it. Strictest and cheapest; occasionally blocks a legitimately broad orientation query.
off — no window checking. The DBID filter is still mandatory regardless of this setting.

Operating

Running a case

uv run observa new              # launch the TUI
uv run observa new --debug      # plus a full trace in observa-debug.log
uv run observa config show      # effective config, secrets redacted
uv run observa setup check      # health checks

What the intake screen asks for

The quality of the run is set here. Agents are held to this text for the whole case.

Problem statementrequired

What went wrong, in your words. Symptoms and timing beat theories — "batch job X took 4h instead of 40min, 14:00–18:00" is worth more than "I think it's I/O".

Investigation scoperequired

The question you want answered. The Master is held strictly to this when consolidating, and will report an unknown rather than drift into an adjacent finding that happens to be interesting.

Known factsoptional, repeatable

Anything already established: a deployment, a failover, a storage migration, a parameter change. These enter the prompt as ground truth and stop agents from spending turns rediscovering them.

DBID + problem windowrequired

Chosen from an interactive timeline of the snapshots the repository actually holds, so you cannot select a window with no data behind it.

Baseline windowauto-suggested

A healthy comparison period. Agents reason in deltas rather than absolute numbers, which is what makes findings like "physical reads up 11×" possible at all.

Diagnostic filesoptional

Each tagged by type: alertlog, trace, tfa, hanganalyze, sqlhc, ddl, awr_report.

Only the paths are given to the agents. Nothing is parsed, chunked or uploaded — agents list, grep and seek their way through the files themselves, which is why a multi-gigabyte alert log is not a problem.

Operating

The pipeline

init→ topology_probe→ diff_probe→ ora_timeline→ turn_1→ gate_1→ turn_N→ consolidate→ synthesize_hypotheses→ detect_contradictions→ resolve_contradiction?→ replay_verify
deterministic — no LLM parallel agent fan-out conditional

The deterministic probes

Three nodes run before any agent sees a prompt. They cost no tokens and they are the reason the fan-out isn't wasted on questions the repository can answer flatly.

topology_probefail-open

Reads version, instance list, and RAC / Exadata / Data Guard flags. Specialists whose subsystem is absent are skipped with a recorded reason, before spending a single token.

diff_probefail-open

Computes problem-versus-baseline deltas and seeds them into every agent's prompt as ground truth for orientation. It also raises a flag when the two windows' load profiles differ so wildly that comparing them is meaningless.

ora_timelinefail-open

Scans the attached alert logs for ORA- and incident lines, labels each as problem, baseline or outside, and computes coverage.

Coverage is the part that matters: it distinguishes "there were no errors during the incident" from "this log doesn't reach the incident window at all". The first is evidence; the second is a hole, and the report says so.

All three fail open. No alert log, no repository answer, no incidents — the node no-ops and the case proceeds.

Turns and gates

Each turn fans every active specialist out in parallel under the watchdog. Agents that time out or raise emit an explicit abstain, so the blackboard records that nobody looked rather than leaving a silence that reads like absence of evidence.

After each turn, a gate checks whether any agent raised a question for you. If so the run pauses, shows the questions, and your answer joins the blackboard for the remaining turns.

Consolidation and the verification tail

The Master receives the complete blackboard digest and returns a summary of at most three findings, tied strictly to the investigation scope, with explicit unknowns and a calibrated confidence. The cap is deliberate: a list of twelve observations is a dump, not a diagnosis.

Then the mechanical tail runs. Hypotheses are synthesized and scored, contradictions between them are detected and — past contradiction_threshold — resolved. Finally replay_verify re-executes the evidence each finding cites and scores whether it genuinely supports the claim. Below verification_support_threshold, that score is applied as a multiplier to the reported confidence. A summary built on evidence that didn't survive re-reading says so in its number.

Operating

The evidence ledger

Every tool call is recorded with a stable identifier, returned to the agent as the first field of the payload:

PrefixAccessRecorded
Q-###query_awrCanonical SQL, row count, truncation flag, warnings
F-###read_filePath, byte offset, extent read
S-###search_filePattern, path, line and byte offsets of each match

Findings cite these in evidence_refs. References to evidence that was never gathered are dropped during turn validation — an agent cannot invent a citation. Findings that end up with none are rendered ○ uncited, in the TUI and in the exported report alike.

The ledger also serves as a within-case cache, keyed on canonical SQL or on (pattern, path), and namespaced by access path so that agent queries and internal catalog lookups never serve each other's results. Two agents asking the same question pay for it once.

Press Ctrl+D at any point to open the evidence browser and read any entry in full.

Why search_file matters

search_file returns both a line number and a byte offset, and that offset feeds straight back into read_file(offset). An agent finds an ORA-00600 at byte 3.2 billion and jumps directly to its context instead of paging through the log. The scan is capped at 200 matches and 64 MB scanned, with no timeout.

Operating

Guardrails

Agents write their own SQL — nothing is templated or hard-coded. Every statement is therefore parsed with sqlglot and validated before it reaches the database.

Read-onlystructural

Only SELECT and WITH survive. INSERT, UPDATE, DELETE, MERGE, DDL and PL/SQL blocks are rejected by expression type, not by string matching.

Allowlisted objectsstructural

DBA_HIST_*, plus DBA_REGISTRY, DBA_FEATURE_USAGE_STATISTICS and DBA_TAB_COLUMNS. The last is there so agents can look up real column names before writing a query rather than guessing and producing ORA-00904.

Extend it by editing ALLOWED_EXACT or ALLOWED_PREFIXES in observa/mcp/allowlist.py. Keep additions read-only and AWR-resident — anything reflecting the local instance defeats the repository model.

DBID predicatemandatory

Once a case is active, a query without a correct dbid filter is rejected outright. Not configurable.

Snap-window predicateconfigurable

Governed by mcp.enforce_window. See mcp.

Row capmandatory

mcp.query_row_limit, with explicit truncation flagged in the result.

Output, and why there is no database

From the summary screen you export into the current directory:

FileContents
<CASE-ID>-report.htmlSelf-contained report: findings, methodology, the ORA timeline with per-window badges, and the full evidence ledger as an appendix.
<CASE-ID>-summary.mdThe final summary in Markdown, for pasting into a ticket.
<CASE-ID>-chat.txtTranscript of the post-analysis conversation.

A case lives in memory for the duration of the session and is then gone. No case database, no checkpointer on disk, no artifact store, no cache that outlives the run. CASE-YYYY-MMDD-NN identifiers exist only to name those three files and tag log lines.

This is a deliberate trade. Diagnostic data is frequently sensitive, and a tool that quietly accumulates a corpus of your customers' AWR internals is a liability rather than a feature. If you want durability, export the report.

Troubleshooting

Startup fails naming saved connections

The name in mcp.sqlcl_connection_name doesn't exist. The error lists what SQLcl does have saved — pick one of those, or create it with conn -save. Observa refuses to guess.

Config rejected at boot with a list of compatible models

An oci/ model was assigned to a slot whose capability requirements it doesn't meet — usually a model without tool calling in the agent slot. The error names the offending slot and lists valid alternatives. See llm.

Every agent abstains

Usually one of three things. The DBID doesn't match any data in the repository; the chosen snap window has no snapshots behind it; or the MCP client failed to attach, in which case agents run with no tools and abstain across the board. Run observa setup check and confirm the DBID against DBA_HIST_DATABASE_INSTANCE.

Agents time out repeatedly

Raise turns.time_budget_seconds, or lower turns.max_concurrent_agents if the wall-clock is being spent in rate-limit backoff rather than in reasoning. The LLM wrapper sleeps 60 seconds on a 429 to let the TPM window recover, which consumes the budget quickly at high concurrency.

Garbled timestamps or shifted CSV columns

An NLS normalization problem. Observa pins the session formats on connect precisely to avoid this; if you see it anyway, check whether a login trigger or glogin script is overriding them after the fact.

ORA-00904 in agent queries

An agent guessed a column name. It is instructed to discover real columns through DBA_TAB_COLUMNS first; a recurring pattern on a specific view is worth a look at the agent's specialty prompt.

Full trace of a run

uv run observa new --debug writes observa-debug.log. The MCP subprocesses keep their own logs in observa-sqlcl.log and observa-files-server.log. All three are git-ignored.
